# Plan: Unity Skills + AGENTS.md for Lamplight

## Overview

Create 4 project-specific opencode skills and an AGENTS.md for the Lamplight (Moonlighter) Unity project. The skills encode the project's established architectural patterns and testing conventions so opencode can generate code that fits seamlessly.

## Note: Unity MCP

The `unityMCP` server is configured in opencode.json but the Unity-side plugin is **not installed** in this project. To activate it:
1. Install via Package Manager: `https://github.com/CoplayDev/unity-mcp.git?path=/MCPForUnity#main`
2. Start the Python server or use Unity's MCP window

Once active, it provides 47 tools (scene editing, test running, script creation, etc.). The skills below are designed to work without MCP (pure code generation) but include optional MCP integration points where it would add value.

### 2. Skill: unity-test-scaffold

**Path:** `.opencode/skills/unity-test-scaffold/SKILL.md`
**References:** `.opencode/skills/unity-test-scaffold/references/test-patterns.md`

**What it does:** Generates EditMode or PlayMode tests following the project's established patterns.

**Argument hint:** `[editmode|playmode] <SystemName>`

**Workflow:**
1. Parse arguments: test mode (editmode/playmode), target system name
2. Find the source files for the target system (search `Assets/Scripts/`)
3. Read the source code to understand public API and events
4. Determine test class: which existing patterns apply
   - If target is in `Rules/` -> pure unit test, no MonoBehaviour, use StubRng if RNG-dependent
   - If target is a Manager -> use TestBootstrap to create singleton, EventRecorder to verify events, GameEventsReset in [TearDown]
   - If target is a PlayerState -> PlayMode test with TestBootstrap, verify state transitions
5. Generate test file with:
   - Correct namespace and assembly references
   - `[TestFixture]` / `[Test]` attributes
   - `[SetUp]` and `[TearDown]` with GameEventsReset
   - EventRecorder usage where applicable
   - Descriptive test names: `Method_Condition_Expected`
6. Place file in correct directory (`Assets/Tests/EditMode/` or `Assets/Tests/PlayMode/`)

**Reference file (test-patterns.md):** Documents the 4 test archetypes with code templates:
- Pure logic test (Rules/ classes)
- Manager integration test (singleton + events)
- Player state transition test (PlayMode)
- UI test pattern

### 3. Skill: unity-script-scaffold

**Path:** `.opencode/skills/unity-script-scaffold/SKILL.md`
**References:** `.opencode/skills/unity-script-scaffold/references/scaffold-templates.md`

**What it does:** Scaffolds new C# scripts following project patterns.

**Argument hint:** `<type> <Name> [options]`
- Types: `manager`, `state`, `interactable`, `uipanel`, `rules`, `def`

**Workflow:**
1. Parse arguments: script type, name, any options
2. Based on type, generate from the appropriate template:
   - **manager:** Singleton MonoBehaviour with Awake, GameEvents integration, domain object ownership
   - **state:** PlayerState subclass with Enter/Exit/LogicUpdate/PhysicsUpdate, transition logic
   - **interactable:** IInteractable implementation with InteractType, factory Create() method
   - **uipanel:** IMGUI OnGUI panel with toggle, GameEvents subscription
   - **rules:** Static class with pure C# methods, no Unity dependency
   - **def:** Immutable data definition class (like ItemDef, ResidentDef)
3. Add necessary event declarations to GameEvents.cs
4. Add using statements matching project conventions
5. Place file in correct directory under `Assets/Scripts/`
6. Register in ContentDb if it's a def type

**Reference file (scaffold-templates.md):** Contains code templates for each of the 6 script types, extracted from existing codebase patterns.

### 4. Skill: unity-arch-review

**Path:** `.opencode/skills/unity-arch-review/SKILL.md`
**References:** `.opencode/skills/unity-arch-review/references/unity-pitfalls.md`

**What it does:** Reviews code for Unity-specific architectural issues and project convention violations.

**Argument hint:** `[file or directory to review, blank for staged changes]`

**Workflow:**
1. Determine scope: specific file, directory, or git diff
2. Run a multi-category check:
   - **Singleton correctness:** Duplicate-destroy in Awake, null-check pattern, DontDestroyOnLoad usage
   - **Event bus hygiene:** Subscribe in OnEnable, unsubscribe in OnDisable, no lambda closures that leak
   - **Coroutine safety:** No dangling coroutines, StopCoroutine before StartCoroutine, null-reference after Destroy
   - **Rules/ layer purity:** No UnityEngine types in Rules/ classes, no MonoBehaviour references
   - **Manager responsibilities:** Single responsibility, no cross-manager direct calls (use events), no UI logic in managers
   - **Player state FSM:** Correct transitions, no direct state field mutation, Enter/Exit symmetry
   - **IInteractable contract:** Correct InteractType, factory method pattern, proper collider setup
   - **Test coverage:** GameEventsReset in TearDown, EventRecorder for event assertions, StubRng for RNG-dependent code
   - **Unity lifecycle:** OnEnable/OnDisable pairing, Awake vs Start semantics, OnDestroy cleanup
3. Report findings with severity and suggested fixes

**Reference file (unity-pitfalls.md):** Comprehensive catalog of Unity-specific pitfalls organized by category, with examples of correct and incorrect patterns.

### 5. Skill: unity-system-design

**Path:** `.opencode/skills/unity-system-design/SKILL.md`
**References:** `.opencode/skills/unity-system-design/references/system-template.md`

**What it does:** Designs a complete new game system following the project's layered architecture.

**Argument hint:** `<SystemName> <brief description>`

**Workflow:**
1. Parse arguments: system name, brief description
2. Research existing systems for similar patterns (search codebase)
3. Design the system's layers:
   - **Domain model** (Rules/): Pure C# state + rules class, no Unity dependency
   - **Manager** (Scripts/): MonoBehaviour singleton bridging Unity lifecycle to domain
   - **Events** (GameEvents): New events for cross-system communication
   - **Interactables** (if player-facing): IInteractable implementations
   - **UI** (if needed): IMGUI panel or HUD elements
   - **Tests**: EditMode for Rules/, PlayMode for integration
4. Generate a design document describing:
   - System responsibilities and boundaries
   - File list with paths
   - Class/API signatures
   - Event flow diagram (text-based)
   - Integration points with existing systems
5. Optionally scaffold all files using the unity-script-scaffold skill

**Reference file (system-template.md):** Template for the system design document, with a worked example based on an existing system (e.g., FermentManager).
